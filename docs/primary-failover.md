# Primary 강제 종료 실험 — 1회 절차 검증

2026-10-22 MySQL 8.4.0 / Docker Desktop의 단일 PC 환경에서 실제 SIGKILL을 주입했다. 요청을 계속 보내는 상태에서 Primary 자동 선출, 새 연결의 쓰기 재개, 승인 기록 보존을 확인했다. 반복 실험과 장애 노드 복귀는 이번 범위 밖이다.

## 조건과 재현

- 시작 상태: 3개 ONLINE, mysql-1 PRIMARY, mysql-2/3 SECONDARY
- 요청: 4개 작업자, 총 1,600건, 건당 100포인트, 작업자별 요청 후 0.05초 간격
- 연결: 요청 시도마다 Router를 통해 새 연결 생성
- 재시도: 같은 요청 ID와 금액, 최대 40회, 시도 사이 0.5초 대기
- 장애 주입: COMMIT 응답 기록이 최소 20건 생긴 뒤 현재 Primary 역할을 다시 확인하고 SIGKILL
- 자동 재시작 비활성화, 강제 Quorum 복구 및 수동 Primary 지정 없음
- 워밍업을 분리한 성능 실험이 아닌 장애 실험 절차 검증

PowerShell에서 실행한다. 현재는 이전 실험으로 mysql-1이 중단돼 있으므로 3노드 복귀를 별도 검증한 뒤에만 재실행할 수 있다.

```powershell
.\scripts\primary_failover.ps1
```

스크립트는 최초 상태 확인, 부하 실행, 현재 Primary 재확인, 강제 종료, 생존 노드 상태 조회, 결과 대조를 수행한다. 현재 Primary의 서비스명을 DB 조회로 결정하며 mysql-1로 고정해 종료하지 않는다. mysql-1은 최초 관리 조회의 시드다. Windows에서 실행 검증했으며 Linux에서는 PowerShell과 Docker Compose가 필요하다. Bash 전용 실행 절차는 아직 없다.

## 실제 결과

| 항목 | 관측 결과 |
|---|---:|
| 종료한 Primary | mysql-1, exit 137 |
| 자동 선출된 Primary | mysql-3 |
| 장애 전 성공 응답 기록 | 68건 |
| 장애 감지 관측 시간 | 8.337078초 |
| 새 Primary 선출 관측 시간 | 24.618118초 |
| 첫 정상 쓰기 / 앱 복구 관측 시간 | 22.843352초 |
| 연결 실패 시도 / 재시도 | 80회 / 80회 |
| 최종 실패 요청 | 0건 |
| COMMIT 응답 확인 / DB 지급 확인 | 1,600건 / 1,600건 |
| 승인 거래 누락 / 중복 지급 | 0건 / 0건 |
| 잔액 불일치 / 입력 불일치 | 0건 / 0건 |
| 최종 결과 미확정 | 0건 |

80회는 실패한 시도 수이며 최종 실패 요청 수와 다르다. 연결 거부 2003 오류 72회와 인증 패킷 수신 중 연결 유실 2013 오류 8회를 관측했다. 모두 같은 요청 ID로 재시도해 최종 성공했다. 이번 실행에서 COMMIT 결과 불명확 오류는 0회였으므로 실제 COMMIT 응답 유실을 검증했다고 주장하지 않는다.

생존한 mysql-2와 mysql-3 각각에 직통 연결해 1,600건의 지급과 잔액을 독립 검증했으며 모두 통과했다. 관측 시점이 다른 두 GTID 문자열은 일치하지 않았으므로, 저장한 기준 GTID에 대해 `WAIT_FOR_EXECUTED_GTID_SET` 및 `GTID_SUBSET`으로 각 노드가 기준 집합을 적용했는지 확인했다. 두 노드 모두 적용을 확인했다. 종료한 mysql-1의 동기화는 검증하지 않았다.

## 이벤트 타임라인

아래 시각은 한국 시간이다. 경과 시간의 기준은 SIGKILL 명령 호출 직전이다.

| 시각 | 이벤트 | 기준부터 경과 |
|---|---|---:|
| 17:32:16.872312 | SIGKILL 명령 시작 | 0초 |
| 17:32:18.122494 | 종료 명령 성공 확인 | 1.250182초 |
| 17:32:25.209390 | 상태 조회에서 기존 Primary의 비정상 상태 확인 | 8.337078초 |
| 17:32:39.715664 | Router 경유 첫 COMMIT 응답 확인 | 22.843352초 |
| 17:32:41.490430 | 상태 조회에서 mysql-3 PRIMARY 확인 | 24.618118초 |

쓰기 재개가 선출 관측보다 빠른 것은 순서를 뒤집은 것이 아니다. 상태 조회는 별도 컨테이너를 실행해 주기적으로 수행하므로 간격과 실행 비용이 포함된다. 실제 선출은 그 전에 이뤄졌으며 MySQL 로그에도 선출 이벤트가 남아 있다. 각 시간은 내부 이벤트의 정확한 소요 시간이 아닌 관측값이다. 감지와 선출 관측 시각은 조회 명령 반환 시각이다.

장애 주입 기준에도 약 1.25초의 Docker 명령 처리 구간이 포함된다. 앱 복구는 종료 명령 성공 확인 이후의 첫 신규 COMMIT 응답으로 판정했다. 기존 지급 재조회 성공은 쓰기 복구로 사용하지 않았다. 클라이언트 응답 시각은 함수 반환 후 기록한 시각이며 서버 내부 커밋 시각과 다르다. 호스트와 컨테이너의 시계가 일치하는 로컬 환경을 전제로 한다.

## 근거 파일과 한계

실행 디렉터리: `results/primary-20261022T083212Z-69043167/`

- `manifest.json`, `events.jsonl`: 입력과 클라이언트 응답·오류·재시도
- `cluster-events.jsonl`: 장애 주입과 멤버 역할·상태·GTID·복제 applier 오류 관측
- `verification.json`, `verification-mysql-2.json`, `verification-mysql-3.json`: 최종 정합성
- `final-mysql-2.json`, `final-mysql-3.json`, `gtid-check-*.json`: 생존 노드 상태와 기준 GTID 적용
- `services.log`, `workload.log`: DB·Router 및 클라이언트 로그
- `failover-summary.json`, `failover-summary.csv`: 집계 결과

사전 회귀 테스트 18개와 시간 집계 단위 테스트를 통과했다. results 원본 파일은 로컬에 보존하며 기본 Git 제외 대상이다. 이 문서의 수치는 실제 단일 실행 결과다. 5회 반복 통계, 부하 대비 성능, 운영 SLA, 보장 가능한 RPO로 일반화하지 않는다.

현재 mysql-1은 중단 상태로 보존했고 mysql-3 PRIMARY, mysql-2 SECONDARY가 ONLINE이다. 다음 단계는 종료 노드를 복귀시켜 역할과 동기화를 검증하는 것이다.
