# 재시도 시간 예산과 미완료 요청 재처리

2026-10-22 최대 40회 재시도의 한계를 보완하려고 기본 정책을 요청별 60초 재시도 예산으로 바꿨다. 저장된 요청을 같은 ID로 재처리하는 명령도 추가했다. 네트워크 분할을 1회 다시 실행했지만 이번에는 새 Primary 선출이 관측되지 않고 작업자 예외도 발생해 자동 실험은 FAIL이었다. 복구 후 재처리로 모든 지급의 최종 결과를 확인했다.

**정책 구현과 재처리 검증은 완료했지만, 60초 정책으로 장애 실험이 자동 완주한다는 검증에는 성공하지 못했다.** 이전 실패와 이번 실패를 모두 보존한다.

## 시간 예산의 의미

기본 실행은 `--retry-budget 60`이다. 요청 처리를 시작할 때 monotonic 시계로 마감 시각을 정하고, 매 시도 전과 오류 후 남은 예산을 검사한다. 대기 시간은 `min(0.5초, 남은 시간)`으로 제한한다. 40회 이상 오류가 발생하더라도 예산이 남아 있으면 같은 ID·사용자·금액으로 다시 시도한다. 인증 오류와 입력 불일치 등은 즉시 종료한다.

COMMIT 결과 불명확 이력이 있으면 예산 만료 시 UNKNOWN, 그렇지 않으면 FAILED로 기록한다. 종료 원인도 `retry_budget_exhausted`, `attempt_limit_exhausted`, `non_retryable_error`로 구분한다.

이 예산은 **새로운 시도를 허용하는 시간**이다. 진행 중인 연결·쿼리·COMMIT을 강제로 취소하지 않으므로 요청이 반드시 60초 안에 반환된다는 보장은 없다. 이미 진행 중인 호출이 예산 이후 성공하면 그 성공을 기록한다. 단단한 전체 요청 마감이 필요하면 드라이버 I/O 제한과 취소·결과 재확인 정책을 추가해야 한다. 이번 60초는 운영 SLA가 아닌 로컬 실습값이다.

기존 횟수 정책을 재현할 때는 `--max-attempts 40`을 사용할 수 있다. CLI에서 두 정책을 동시에 지정할 수 없고, 명시적인 횟수 모드에서는 시간 예산을 사용하지 않는다. 기존 Primary·Secondary 실험 스크립트는 횟수 모드를 유지하며 네트워크 분할 스크립트는 60초 모드를 사용한다. 아래 드라이버 변경 때문에 현재 실행 환경이 최초 실험과 완전히 같다는 뜻은 아니다.

## 재처리 명령

작업자가 모두 종료되고 클러스터가 정상화된 뒤 실행한다.

```sh
docker compose run --rm workload python -m workload.reprocess results/<source_run> --retry-budget 60
```

원본 manifest에서 COMMIT 응답 확인 또는 기존 지급 확인 기록이 없는 요청을 고른다. FAILED, UNKNOWN, 시도 기록이 없는 요청이 대상이다. 원래 ID·사용자·금액을 그대로 사용하고 계정을 새로 생성하지 않는다. 이미 DB에 지급됐다면 기존 지급 확인으로 끝내며 잔액을 추가 증가시키지 않는다.

새 `results/reprocess-.../` 디렉터리에 원본 manifest와 이벤트를 복사하고 출처·선택 ID·예산을 기록한다. 새 이벤트는 `phase=reprocess`로 구분한다. 원본 파일은 수정하지 않는다. 승인 기록은 있는데 DB에서 사라진 요청은 자동 재처리 대상으로 숨기지 않고 검증 실패로 남긴다. 전체 원본 요청과 DB를 다시 대조해 최종 판정한다.

복사된 로그의 기존 오류·재시도 횟수는 누적 보고서에 남는다. 재처리 횟수와 이번 단계의 신규 시도는 재처리 manifest와 phase 이벤트로 확인한다. phase별 경과 시간의 기준점은 서로 다르므로 전체 타임라인에는 UTC 시각을 사용한다.

## 두 번째 네트워크 분할 결과

총 1,600건, 4개 작업자, 건당 100포인트, 요청 후 0.05초 간격은 이전과 같다. 시작 시점의 Primary를 동적으로 고르므로 이번 대상은 mysql-2였고 생존 노드는 mysql-1/3이었다. 이전 대상은 mysql-3이었다. 같은 물리 노드·같은 네트워크 상태를 통제한 비교가 아니다.

| 항목 | 이전 횟수 모드 | 이번 60초 모드 |
|---|---:|---:|
| 격리 대상 | mysql-3 | mysql-2 |
| 새 Primary | mysql-2 | 대기 기한 내 관측 못함 |
| 최초 COMMIT 응답 기록 | 1,599건 | 1,217건 |
| 재처리 전 DB 지급 확인 | 1,599건 | 1,218건 |
| 최종 실패 기록 | 1건 | 예산 만료 3건 |
| 시도 기록 없는 요청 | 0건 | 379건 |
| 오류 시도 / 자동 재시도 | 104 / 103 | 432 / 429 |
| 승인 거래 누락 / 중복 / 잔액 불일치 | 0 / 0 / 0 | 0 / 0 / 0 |
| 자동 실험 판정 | FAIL | FAIL |

이번에는 두 생존 노드에서 서로에 대한 UNREACHABLE/복구 경고와 Group Replication 연결 오류가 반복됐다. 새 Primary를 90초의 대기 기한 안에 관측하지 못해 `finally`에서 네트워크를 복구했다. 이후 기존 mysql-2가 Primary인 ONLINE 3개 상태로 돌아왔다. Quorum 강제 조작이나 수동 승격은 하지 않았다. 이 생존 노드 간 연결 불안정의 근본 원인은 아직 확정하지 못했다.

소수 노드 로컬 프로브는 새 Primary 선출 뒤 실행하는 절차이므로 이번에는 실행하지 않았다. 집계는 `NOT_EXECUTED`, 선출·격리 중 쓰기 재개 시간은 null로 남긴다. 선출 실패를 임의의 복구 시간으로 대체하지 않는다. 정합성 PASS는 서비스 가용성 PASS를 뜻하지 않는다.

작업자 하나는 연결 해제 뒤 정리 과정에서 `_mysql_connector.MySQLInterfaceError`가 노출돼 중단됐다. 그 결과 379건은 실제 시도 기록이 없었다. 검증기의 `unknown_outcome_requests=379`는 이 미시도 요청을 포함한 미해결 결과이며, 379건의 COMMIT 응답이 유실됐다는 뜻이 아니다.

DB 지급은 성공 기록보다 1건 많았다. 이 1건에서 서버 커밋과 클라이언트 파일 기록이 분리됐음을 확인했지만, COMMIT 응답 수신 여부 자체는 기록이 없어 단정하지 않는다.

## 드라이버 정리 예외 수정

실험 뒤 기본 연결을 Connector/Python 9.1.0의 순수 Python 모드(`use_pure=True`)로 바꿨다. C 확장의 원시 정리 예외가 공개 드라이버 예외 처리 경로를 벗어난 관측을 피하려는 선택이다. 종료 시 연결 해제 오류도 원래의 UnknownOutcome을 덮지 않도록 처리했다. COMMIT 응답 확인 뒤 연결 정리 오류가 나더라도 지급 결과를 실패로 바꾸지 않는다.

이 변경은 이번 분할 주입이 끝난 뒤 적용했고 아래 재처리에 사용했다. 순수 Python 모드로 또 네트워크 장애를 주입한 것은 아니므로 드라이버 변경이 실제 장애 중 작업자 중단을 해결했다고 확정하지 않는다. 모의 정리 오류 회귀 테스트와 정상 DB 실행으로 검증했다. 기존 성능 수치와 직접 비교하지 않는다.

## 실제 재처리 검증

이번 실험의 미확인 요청 383건을 선택했다. 이미 DB에 있던 1건은 기존 지급으로 확인했고, 나머지 382건을 새로 지급했다.

| 항목 | 재처리 뒤 결과 |
|---|---:|
| COMMIT 응답 기록 | 1,599건 |
| 기존 지급 재확인 | 1건 |
| DB 최종 지급 | 1,600건 |
| 최종 실패 / 미해결 결과 | 0 / 0 |
| 승인 거래 누락 / 중복 / 잔액 불일치 | 모두 0건 |

이전 실험의 실패 요청 1건도 같은 원본 ID로 지급했다. 이어 같은 원본을 다시 재처리했을 때는 `confirmed_existing`이 반환됐고 추가 지급은 없었다. 두 실험 데이터 각각에서 세 노드의 지급 1,600건과 잔액을 확인했고, 기준 GTID 적용과 Router 점검 쓰기도 통과했다.

원본 manifest·이벤트·최초 검증 보고서는 재처리 전후 해시가 같았다. 최초 자동 실험의 FAIL을 PASS로 덮어쓰지 않았고 재처리 결과만 별도로 PASS로 기록했다.

이후 추가 장애 없는 [통신 진단](network-diagnosis.md)을 수행했다. 현재 6방향 접속과 복구 계정 인증은 정상이지만 과거 연결 실패의 최하위 원인은 아직 확정하지 못했다. 다음 과제는 장애 순간의 추가 관측을 준비하고 정상 초기 조건에서 자동 실험을 다시 검증하는 것이다. 전체 Quorum 상실 실험으로 범위를 넓히지는 않았다.
